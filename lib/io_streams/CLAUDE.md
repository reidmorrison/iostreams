# lib/io_streams

How the internals of IOStreams fit together, for work on the files under `lib/io_streams/`. The public API boundary, backward compatibility, and the conventions that apply everywhere are in the [root CLAUDE.md](../../CLAUDE.md).

Core pipeline (lib/io_streams/):
- `builder.rb` - `Builder` parses file-name extensions (e.g. `.csv.gz.enc`) into an ordered pipeline of reader/writer streams, merging in user-supplied `#stream`/`#option` settings, and asks each stream's format to open it. `#option` adjusts an auto-detected stream; `#stream` replaces auto-detection entirely (`:none` disables it). The two are mutually exclusive on one instance.
- `schema.rb` - `Schema`, a Frictionless Table Schema set with `Stream#schema` (a Hash, or the path or url of a JSON file read when first needed), holds the fields of rows and records (the name, type, `aliases` and `constraints` of each one) and `fieldsMatch`, finds the field of a column or key (`#field_for`: exact name or alias, then compared without case, spaces and punctuation, then by the cleansed name, so a field named as `cleanse_header` named a column matches it, which also settles a column that is several fields once compared loosely), and checks a file's columns against `fieldsMatch` (`#check_columns`). `Schema::Columns`, one per reader or writer, holds one file's columns matched to the fields once, and converts its rows and records, which `Tabular::SchemaMapping` asks it to do after its parser parses a line and before it renders one, for every format; the keys of the records read are the field names, and the header row written is the field names, and `writer(:array)` writes that header row itself and takes each row as the values of the fields in order, while a header row written to it (`Row::HeaderRow`, or a copy's `#write_header`) gives the columns of the rows after it, matched to the fields, so that rows read and copied are written in the columns of their fields. The fixed width parser takes the position of each field from the schema. With a schema, the per-call column options (`columns:`, `allowed_columns:`, `required_columns:`) raise `ArgumentError` unless nil (`Tabular::Header.column_option_names`; `skip_unknown:` only applies to `allowed_columns:`, so it is accepted), so that Rocket Job can supply the same options with and without a schema; `cleanse_header:` raises even when nil, since nil means "do not cleanse", which is a setting, while omitting it is `Tabular::CLEANSE_BY_DEFAULT`. The deprecated `Stream#format_options` layout is translated into a schema by `Tabular::Parser::Fixed.schema` (with `fieldsMatch: "subset"`, so writes skip unknown keys as a layout did) each time a reader or writer is built, and still accepts them (`Tabular::LayoutMapping`); it raises for a format other than `:fixed`. Settings that describe the file are set on the path: `#encoding` on the builder, and those of its rows (`#format`, `#schema`, the deprecated `#format_options`, and the options of a row format such as `option(:parquet, ...)`) on its `Tabular::Settings`, one per stream, created when first needed, which checks each one when it is set, resolves the format of the rows (`#rows_format`), and builds the `Tabular` of each call (`#tabular`). `Tabular::FORMAT_OPTION_NAMES` lists the settings that `#each`/`#reader`/`#writer` reject per call, with an example of setting each on the path in `Stream::PATH_SETTINGS`; the line, row and record readers and writers declare the options of each call in their mode in `option_names`, and those of them that are deprecated in `deprecated_option_names` (each asks `Tabular.deprecated_option_names` for the column options, and the row and record readers add `embedded_within`), and `Stream#reject_unknown_options!` raises for any other before anything is opened, listing only the options that are not deprecated; `Stream.read_option_names` lists those that writers and copies reject, since a copy uses its options to write the target, computed from those `option_names` (`Tabular` asks `Tabular::Header` for its own); docs/streams.md explains the rule to users. `Tabular` also owns the header-row protocol of the readers and writers, such as `#read_row`, `#read_line`, `#start_rows` and `#render_record`, and maps the columns of the file to the values of its rows and records with a `Tabular::Mapping`, one role with three implementations, chosen once when the `Tabular` is created, which it asks instead of branching on what describes the columns: `HeaderMapping` without a schema (by the header row or the columns supplied, which a `Tabular::Header` holds with the deprecated column options; it owns the cleansing of the header row, `cleanse_header:`), `SchemaMapping` (the fields, through `Schema::Columns`; its `Header` keeps the header row as read, for `read_header(header.columns)`) and `LayoutMapping` for the deprecated layout (a `HeaderMapping`, so the column options still apply to its records, whose values a `SchemaMapping` of the layout's schema reads and renders). Each one reads lines into rows and records, renders rows and records, and the header row, and answers the questions of the protocol (`#requires_header?`, `#header?`, `#rows_header?`, `#first_row_header?`, `#columns_from_first_row?`, `#columns_from_header_row?`, `#columns_supplied?`). A parser only turns a line into a row in the form of its format and back, a Hash for a format of keyed records such as JSON (`Tabular::Parser::Base.keyed?`), otherwise an Array in the order of the columns, such as CSV or fixed width, which the mapping arranges, so it never sees a `Header`, and returns an Array that it is given as it is, a row already parsed, so that `record_parse(row)` reads the rows that `each(:array)` yields, as Rocket Job's workers do; whether the format has a header row (`#requires_header?`) is a separate question. `each(:array)` yields an Array for every format, and every file whose columns are known starts with a header row: a file without one (fixed width, JSON and Parquet with a schema, or `header: false`) first yields the names of the fields (`Mapping#read_rows_header`), then the values of the fields in order (`Schema::Columns#match_in_order`, `#read_row`), and JSON or Parquet without a schema first yields the keys of its first record as a header row (`Tabular#rows_header?`, `#read_row`), whose columns `HeaderMapping` holds apart from the record columns that the column options restrict, raising `InvalidHeader` for a key that the first record lacked; `writer(:array)` takes the first row written to JSON as its header row, without a line. The header row that `each(:array)` yields is an `IOStreams::Row::HeaderRow` (`Tabular#read_row`), an Array whose class says so, which `Row::Writer#<<` hands to `#write_header`, so that rows copied by a loop keep their header row whatever the formats. `each(:slice)` (`Slice::Reader`) hands on the rows without parsing them, through `Tabular#read_line`, which reads the header row, or with a schema matches the keys of the first record of a keyed format (`Mapping#check_keys`), and each `Slice` carries its format and `Tabular#header_row`, the header row as read, which `Tabular::Header#row` keeps for every mapping, since `#cleanse!` does not change it; `Slice::Reader.check` checks the options of a call before the file is opened, accepting the column options only when they are nil. `Slice#to_h` returns what a slice holds as a Hash of Strings and Arrays to store it, which `IOStreams.slice` turns back into a slice (`Slice.from_h`), so that a runner stores it without knowing its keys. `IOStreams.stream(slice)` returns a `Slice::Stream`, a `Stream` whose source is the rows of the slice, after its header row (`#open_rows_reader`), in the format of the slice (`Stream#text_format`, which the builder answers for any other stream), so that `Tabular::Settings` still owns the format and schema; it raises for what needs bytes, such as `#stream`, `#encoding` and the `:line` mode, and for writing.
- `parquet.rb` - Parquet is a tabular format (`Tabular::Parser::Parquet`, records of typed values like `:hash`), not an extension registered with `Builder`, since it turns bytes into rows rather than other bytes. A parser class names the format module (a `StreamFormat`, such as `IOStreams::Parquet`) of a format whose rows are not lines with `row_format`; `Stream` asks `Tabular#lines?` and then reads and writes rows through `Tabular#read_rows`/`#write_rows`, which open that module with the options set by `Stream#option(:parquet, ...)`. `Tabular::Settings` holds those options (`#merge_row_options`), apart from the streams of the builder, since they are not part of the byte pipeline, checked by the module as soon as they are set; `Stream.row_format(name)` decides whether `#option` and `#stream` set the options of a row format or of a stream, so they set them alike, a registered extension of the same name takes precedence, and `#inspect` and `IOStreams.redact_stream_options` show them redacted by their format (`Stream.stream_format`). `Tabular.new(row_format_options:)` supplies them to the format, and the schema is passed with `StreamFormat#open_stream(arguments:)`, so it is not an option, to the writer and to the reader. With a `subset`/`partial` schema, `Schema#projection` picks the columns that the reader decodes. `Parquet::Column` maps each schema field to its Parquet type; the writer needs a schema, and runs the `parquet` gem in a thread fed by a queue, since the gem pulls rows from an Enumerator while records are pushed with `#<<`.
- `reader.rb` / `writer.rb` - base classes. Every format stream is a `Reader` (implements `#read`) or `Writer` (implements `#write`) opened via `.open`/`.stream`/`.file` class methods that yield the wrapped stream to a block. The base classes provide automatic fallback: a format that only works on files (e.g. zip, xlsx) gets the input copied to a temp file first. The stream that a reader block receives reads like an IO whichever format it is, since a path is configuration: a reader that receives its data in chunks includes `IOStreams::ChunkReader` (`#read`, `#readpartial`, `#gets`, `#readline`, `#readlines`, `#each_line`, `#eof?`) and supplies `#next_chunk`, and a writer includes `IOStreams::Writable` (`#write`, `#<<`, `#print`, `#puts`, `#printf`) and supplies `#write_data`, or wraps the writer of a gem in `Writable::Adapter`. `test/stream_io_test.rb` checks every registered stream.

Registries at the bottom of `lib/io_streams/io_streams.rb` map file extensions to formats and URI schemes to path classes; new formats are added with `IOStreams.register_extension` / `IOStreams.register_scheme`. A format is a module, such as `IOStreams::Gzip` in `lib/io_streams/gzip.rb`, that answers `reader_class`, `writer_class`, `compressed?` and `encrypted?`, and extends `IOStreams::StreamFormat`, which combines the options of its reader and writer, checks them, and opens the reader or writer with the options it uses. The `:encode` stream (`IOStreams::Encode`) is not registered: file names do not name it, since it converts the text that the application reads or writes, so `Builder` owns it as a built-in stream, applies it whenever its options are set, and always places it closest to the application. `Builder::RESERVED_KEYWORDS` holds the names that `#option`/`#stream` give a meaning of their own, `:encode` and `:none`, and `IOStreams.register_extension` asks `Builder` so that it rejects them. Facts about a format's data, and anything that combines both directions, belong on its module; its `Reader` and `Writer` hold what applies to one direction, such as `option_names`. A format registered with just its reader and writer classes is wrapped in a frozen `IOStreams::Extension`, which is neither compressed nor encrypted.

Reading uses a pull model (each stream reads from the previous one on demand); writing uses a push model. See CONTRIBUTING.md for the design philosophy.

`IOStreams::Pgp` shells out to the `gpg` executable rather than using a library.
